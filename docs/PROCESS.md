# 制作流程：这个项目是怎么一轮一轮做出来的

这份文档记录**做的过程**：先后做了什么、为什么推翻、各个环节谁负责什么。技术实现见 [`TECHNICAL.md`](TECHNICAL.md)，故事设定和设计原则见 [`NOTES.md`](NOTES.md)。

---

## 0. 起点：先问"要什么"，而不是"怎么做"

这个项目的核心判断是：**数据、技术、赛博朋克皮都不重要，重要的是故事和审美。** 所以一开始就定下几条不动的东西：

- 故事：侦探骇进组织系统，线索都指向同一个没有名字的人（"螳螂捕蝉，黄雀在后"）。
- 整站是一个**蜜罐**：访客以为自己在骇入，其实系统是为他搭的。
- **少说，让访客自己发现。** 概念靠"自己发现的异常"传达，比任何旁白都有力。
- 语言按"谁在说话"分：系统说英文（大写等宽字，当纹理），侦探的笔记说中文（真正要读的内容），代号不翻译。
- 配色：黑、白、暖灰，**红色只给那根线**。

## 1. 第一轮：三个方向的小样（`b-noir.html` 等）

做法：同一个故事，做三个**很小的切片**（不是完整版），让评审者看了直接反应，而不是描述。

| 方向 | 结果 |
|---|---|
| B 黑色电影 | 胜出。"五个人六个影子，鼠标移上去第六个影子闪开"这一下最有感觉 |
| A 剪纸片头 | 剪辑思路可以，但代码手画的具象物件撑不起质感；模板化的动效语言过时 |
| C 预告函 | 开场拖沓，太逐字照搬设定；但"选择调查对象"的界面受欢迎 |

**学到的：** 代码画剪影和光影可以，画具象插画不行；给的是概念，不要把概念一句句翻成字幕。

## 2. 方向转向：用图像模型出图，用代码"贴"

第一轮之后的关键判断：**美术交给图像模型，代码负责互动、动效和"胶水"。** 代码手画的插画永远比不过模型出的图，但模型不会做互动。分工因此变成：

| 模型出图 | 代码负责 |
|---|---|
| 背景墙、人物、分镜、海报、胶带贴纸 | 排版、UI、动效、物理、转场、状态、音效 |

这条路带来一整套**抠图流水线**（见 TECHNICAL §4）和一个反复出现的原则：贴上去的东西必须和它的墙同属一个"世界"。

## 3. 第二轮：从角色到首页，一步一步

每一步都遵循同一个节奏：**先出一张看得见的样子 → 反应 → 再写代码**。大件先出静态图，确认再动工。

1. **人物。** 先让模型画四人合影（三种风格各一张），反应后选定"漫画墨线 + 网点 + 一点红"。同一张合影之后作为参考图（`-i`）喂给后续每一次出图，保证是同一个人。
2. **首页第一屏。** 三个构思：会看你的分镜、破解小游戏、被涂黑的案卷封面。选了第一个的变体：**人物背对/面对一面监视器墙，手里握着红线**。
3. **推翻电视墙。** 电视墙做出来后发现：靠"在一张画好的图上叠一层闪烁"，上限就在那里，放大后又糊又怪；而且"电视"本身是烂大街的元素。改成**涂鸦墙 + 分镜贴纸**。电视和主控台留给结局（幕后之人的领地）。
4. **背景的丰富度。** 一张烘焙好的大图放大后细节是糊的。改成：纯质感的墙 + **30 张 GPT 画的小分镜**（每次打开随机贴 22 张，分远近两层，远暗近亮，视差不同）。
5. **人物接地。** 人物看起来悬在地上：因为地面是一片乱反射，没有清晰的"平面"。解法：换一张有踢脚线和清晰地面的底图 + 每只脚各自的接触阴影（三个人的脚高低不同，不能共用一个脚底中心）。
6. **红线的意义。** 红线最初只是"一根线"，握在人物手里显得突兀。最终的含义是**钓线**：他们是放线的人，线的另一头一直在幕后那个人手里。线从手里垂下来，被拉紧，最后**把屏幕沿着它撕开**。
7. **UI 变成"物件"。** 一开始的标签和按钮是平的。做了三种 ENTER 按键（纸质键帽 / 漫画菜单斜切条 / 街机红按钮），在真实页面里点着比，最终选了斜切条，并把对比度压下来（纯白→灰纸底板，亮红→暗红）；选了一个组件，**同一类的其他组件跟着换成同一套语言**。
8. **墙面彩蛋。** 同一套构图换了六种墙面，最后只留一个当默认，其余变成彩蛋（按 `P` 静悄悄淡入下一幅）。

## 4. 嫌疑人列队页：两个模型交叉评审

第二页采用了一套新的协作流程，**让两个 AI 互相挑毛病**：

1. **写任务书**（`brief`）：项目背景、现有文件、素材清单、美术方向、已知 bug，以及一句质量标准：
   > 以 Awwwards、Webby Awards、FWA 获奖网站为质量标准。完成后，从排版、留白、视觉层级、色彩、动效、微交互、响应式和原创性等方面自检并持续优化，直到页面没有明显可提升之处。
2. **第一轮：只提意见，不改文件。** 编码模型读完代码和截图，写一份"诚实的批评 + 它不同意我的地方 + 具体重设计"。它指出了真问题：列队页和首页不是一个世界、手机竖屏溢出、选中动效互相冲突、没有"已读"的状态模型、红线太像发光图表。
3. **美术指导做决定**：逐条采纳/修改/补充（比如把它建议的"全部用干净海报"落实成真的去生成了四张无文字的干净海报）。
4. **第二轮：授权施工。** 编码模型自己循环：搭静态构图 → 四种屏幕尺寸截图 → 修 → 搭动效/交互/彩蛋 → 自检，最多三轮迭代。
5. **验收看画面，不看代码。** 在真浏览器里点一遍：进入、切换、读完三份档案后第四个人出现、彩蛋、窄屏溢出。

这一轮中途网络断过一次（编码模型没来得及写总结报告），所以最终以**页面当时的真实状态**为准重新验证，而不是相信它的自述。

## 5. 性能：量出来，而不是猜

作品完成后发现"一打开就卡"。排查是**实测**的（详见 TECHNICAL §6）：

- Retina 屏下首页只有 23 帧/秒，最差一帧 316 毫秒。逐项关掉怀疑对象，真正的元凶是**每帧被 JS 挪动的图层里套着一堆模糊/阴影滤镜，每一帧都在重画**。给这些图层开独立的合成层，直接到稳定 60 帧。
- 冷启动要 2.2 秒才能搭场景：动画库和字体来自外网 CDN，而场景是 JS 搭的。自托管后降到 0.16 秒，**外网请求归零**。
- 发布到线上之后又量了一次真实网络：本地没有带宽限制，看不出来的问题在这里暴露了：几十张图同时抢带宽，最重要的人物反而最后到。把图改成**分批加载、按到货顺序登场**，限速 5 Mbps 下人物到货从 7 秒降到 1.5 秒。教训：**性能要在接近真实的网络下量，不能只在本机量。**

## 6. 这个流程里反复验证有效的做法

- **反应胜过描述。** 评审者看得出好坏，但说不出"为什么"。出几个明显不同的方向让他反应，再把反应翻译成设计语言，记在一份"审美词典"里。
- **一次只改一件事，改完马上看。** 每个改动都在真实页面里验证；截图只是证据，不是结论。
- **别替评审者选。** 他选了一个方案，要把同一类的东西一起改，而不是只改被点名的那个。
- **量过再改。** "感觉卡"不是结论，"23 帧、最差 316 毫秒、关掉这一项变成 60 帧"才是。
- **互动要有因果。** 红线不再追着鼠标跑（没有理由），改成只有靠近 `ENTER` 才被"放"过去。
- **彩蛋不解释。** 没有任何提示文字，找到的人才有惊喜。
- **被拒绝的方案要彻底删掉。** 别留一条"也许以后用得上"的代码路径。

## 7. 没做完的

- 点开第四个人之后的**结局**：先是一间只有一束光的黑屋子，光照到一个人形的虚影时触发，最后落在一张"主控台"前（弹出对话框、打出一句中文、警报铺满屏幕、故障全部消失、回放访客自己走过的路径）。设计已经定了，没有做。
- 列队页的墙压暗得偏灰；窄屏中文笔记的断行；列队页的红线物理。


## 8. 第七轮：从静态方案到分层列队页

先制作三张静态方案，比较构图和阅读顺序，再确定 D 的漫画分镜突破方向。随后分别设计三个角色的拉线切开、掀角跃出和斩开分镜动作，让入场节奏与姿态对应。

施工时将纸片、内景、透明人物、阴影、倒影、红线、侧卡和档案卡拆成独立图层，再接入正式抠图素材与角色锚点。评审覆盖静态构图、入场及切换序列、文字遮挡、不同桌面尺寸、手机竖屏和减少动态效果；后续修正集中在人物几何、侧卡脸部裁切、图层遮挡和窄屏布局。
